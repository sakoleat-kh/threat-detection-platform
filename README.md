# Threat Detection Platform

A rule-based Threat Detection Platform that analyzes security logs, detects
suspicious activities using detection rules, and maps findings to the
MITRE ATT&CK framework.

This project demonstrates detection engineering concepts including log parsing,
event normalization, rule-based detection, MITRE ATT&CK enrichment, alert
persistence, repository filtering, pagination, and CLI-based ingestion.

## Current Status

### Phase 1 — Log Ingestion and Parsing

Phase 1 established the foundational log ingestion and parsing layer.

Implemented:

- Linux `auth.log` parser
- Apache/Nginx Combined Log format parser
- Syslog timestamp year resolution
- Apache timestamp parsing with timezone support
- Structured authentication and access-log events
- Query-string extraction from HTTP requests
- Referer and User-Agent extraction
- Streaming log readers using generators
- CLI tools for both log types
- Malformed-input handling and targeted logging
- Parser unit tests
- Apache parser hardening tests
- End-to-end Phase 1 integration tests

### Phase 2 — Detection and MITRE ATT&CK

Phase 2 added the detection engineering layer.

Implemented eight detection rules:

1. SSH Brute Force
2. Successful After Failures
3. Excessive Sudo
4. New User Creation
5. Directory Scanning
6. SQL Injection
7. XSS Attempt
8. Suspicious User-Agent

Alerts are enriched with MITRE ATT&CK technique and tactic information.

### Phase 3 — Persistence, CLI, and Performance

Phase 3 completed the end-to-end detection pipeline.

Implemented:

- SQLite database persistence using SQLAlchemy
- Persistent `AlertRecord` model
- Alert repository functions
- Alert lookup by ID
- Alert pagination
- Filtering by rule ID
- Filtering by MITRE technique ID
- Filtering by source IP
- Filtering by event date range
- Combined alert filters
- CLI ingestion using `scripts/ingest.py`
- Ingestion summaries
- Missing-file handling
- Malformed-input handling across the full ingestion chain
- Performance measurements for parsing, detection, and database persistence
- Performance evaluation at 5,000+ line scale
- Phase 3 repository and ingestion tests

The project currently has **164 passing tests**.

## Database Setup

The project uses SQLite for persistent alert storage.

Initialize the database with:

```bash
python -m scripts.init_db
```

This creates the required database tables in `alerts.db`.

## CLI Usage

The main ingestion CLI is:

```bash
python -m scripts.ingest
```

At least one log source must be provided.

### Ingest Both Log Types

```bash
python -m scripts.ingest \
  --auth-log data/sample_logs/auth_sample.log \
  --access-log data/sample_logs/access_sample.log
```

### Ingest Only an Authentication Log

```bash
python -m scripts.ingest \
  --auth-log data/sample_logs/auth_sample.log
```

### Ingest Only an Access Log

```bash
python -m scripts.ingest \
  --access-log data/sample_logs/access_sample.log
```

The CLI reports:

- Authentication events processed
- Access events processed
- Alerts generated by detection rule
- Total alerts generated
- Total alerts saved to the database
- Parse and normalization runtime
- Detection and MITRE enrichment runtime
- Database persistence runtime
- Total runtime

## Performance

A Day 62 performance benchmark was performed using synthetic log files
generated by repeating the existing sample logs 26 times.

### Test Dataset

- Authentication log: 5,174 lines
- Access log: 5,174 lines
- Total input lines: 10,348
- Total successfully processed events: 10,323

### Measured Runtime

| Stage | Runtime |
|-------|---------|
| Parse + normalize | 0.3309 seconds |
| Detection + MITRE | 0.1728 seconds |
| Database persistence | 0.0250 seconds |
| Total runtime | 0.5288 seconds |

Parsing and normalization was the largest measured stage and is therefore
the clearest current performance optimization target for substantially larger
workloads.

See `docs/performance_notes.md` for the complete performance evaluation and
limitations.
