# Alerts Database Schema Design

## Purpose

The `alerts` table stores detection alerts persistently so that alerts remain available after the detection process ends.

Each row represents one alert generated by a detection rule.

## Alerts Table

| Column | Purpose | Suggested Type | Nullable | Indexed |
|---|---|---|---|---|
| `id` | Unique alert identifier | Integer | No | Primary Key |
| `rule_id` | Stable identifier for the detection rule | String | No | Yes |
| `rule_name` | Human-readable rule name | String | No | No |
| `severity` | Alert severity | String | No | Yes |
| `description` | Description of the detection | Text | No | No |
| `technique_id` | MITRE ATT&CK technique ID | String | Yes | Yes |
| `technique_name` | MITRE ATT&CK technique name | String | Yes | No |
| `tactic` | MITRE ATT&CK tactic | String | Yes | Yes |
| `source_type` | Type of source that produced the event | String | No | No |
| `source_ip` | Source IP associated with the event | String | Yes | Yes |
| `username` | Username associated with the event | String | Yes | Yes |
| `event_timestamp` | Time the original event occurred | DateTime | No | Yes |
| `created_at` | Time the alert was stored by the platform | DateTime | No | Yes |
| `raw_event_json` | Original normalized event data | JSON/Text | No | No |

## Indexing Decisions

### `rule_id`

Index this column because analysts may frequently filter alerts by the detection rule that generated them.

### `rule_name`

This column is stored for readability and reporting, but does not receive an index initially because `rule_id` is the stable identifier used for rule-based filtering. A saparate index can be added later if real query patterns require filtering directly by `rule_name`.

### `severity`

Index this column because security workflows commonly need to retrieve high- or critical-severity alerts quickly.

### `technique_id`

Index this column because analysts may investigate alerts associated with a particular MITRE ATT&CK technique.

### `tactic`

Index this column because analysts may filter alerts by an ATT&CK tactic such as Credential Access or Initial Access.

### `source_ip`

Index this column because investigating activity from a particular source IP is a common security investigation task.

### `username`

Index this column because analysts may investigate alerts associated with a particular account.

### `event_timestamp`

Index this column because security investigations frequently query alerts within a specific time range.

### `created_at`

Index this column because the platform may need to retrieve alerts based on when they were generated or stored.

### Fields without indexes

`description`, `technique_name`, `source_type`, and `raw_event_json` do not receive indexes initially because they are less likely to be primary filtering fields in the first version of the system.

Indexes can be added later based on actual query patterns.

## Primary Key

`id` is the primary key and uniquely identifies each stored alert.

The database should generate this value automatically.

## Timestamp Design

The table stores both `event_timestamp` and `created_at`.

- `event_timestamp` represents when the original security event occurred.
- `created_at` represents when the detection platform created the alert record.

Keeping both timestamps allows the system to distinguish the time of the underlying activity from the time the platform processed and stored the alert.

## MITRE Fields 

`technique_id`, `technique_name`, and `tactic` store the MITRE ATT&CK enrichment associated with the alert.

These fields are nullable because an alert may come from a rule that has not yet been mapped to ATT&CK.

## Raw Event Storage

`raw_event_json` stores the original normalized event data associated with the alert.

This preserves useful investigation context without requiring every possible event-specific field to become a separate database column.

## SQLAlchemy Implementation Notes

The schema is designed to map directly to a SQLAlchemy model.

The `id` column will be the primary key.

String fields should use appropriate length limits where practical, while `description` and `raw_event_json` may require larger text-capable types.

`event_timestamp` and `created_at` should use timezone-aware DateTime columns where supported by the selected database.

The initial index strategy should prioritize fields commonly used for security investigation and time-based queries. Indexes can be revisited after observing real application query patterns.
